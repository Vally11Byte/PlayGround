# 06 · CI con GitHub Actions

🎯 **Obiettivo:** far controllare a GitHub, in automatico, che ogni modifica compili.

## 📖 Concetti

**CI (Continuous Integration)**: ad ogni push e ad ogni PR, un computer di GitHub scarica il codice,
lo compila, esegue i test. Se qualcosa si rompe **lo sai subito**, prima del merge, non quando
un collega fa `git pull` e non gli parte più niente.

**GitHub Actions** è il sistema di GitHub per farlo. Si configura con file YAML in `.github/workflows/`.

| Termine | Cos'è |
|---------|-------|
| **Workflow** | un file `.yml`: un processo automatico |
| **Trigger** (`on:`) | quando parte: push, pull_request, tag, a mano... |
| **Job** | un gruppo di step che gira su una macchina (`runs-on`) |
| **Step** | un singolo comando (`run:`) o un'azione già pronta (`uses:`) |
| **Runner** | la macchina virtuale che esegue il job |

## 📖 Leggiamo `ci.yml`

Apri [`.github/workflows/ci.yml`](../.github/workflows/ci.yml):

- `on: push` su `main` e `pull_request` verso `main` → parte in questi due casi
- job **`build`**: installa .NET 10, `restore`, `build`, `test`
- job **`docker`**: `needs: build` → parte solo se `build` è riuscito. Costruisce l'immagine **senza pubblicarla**:
  serve solo a garantire che il Dockerfile non sia rotto
- `cache-from/cache-to: type=gha` → riusa i layer Docker tra un'esecuzione e l'altra

## 🛠️ Pratica

### 1. Guardala girare

Il workflow è già nel repo, quindi è già partito al tuo ultimo push.
```bash
gh run list               # le ultime esecuzioni
gh run watch              # segui quella in corso
```
Oppure su GitHub, tab **Actions**. Clicca un'esecuzione → un job → espandi gli step per leggere i log.

### 2. Rompi la build (apposta)

```bash
git switch -c test/rompi-build
```
In `Home.razor` scrivi un errore nel blocco `@code`, es. `private int x = "ciao";`
```bash
git commit -am "test: build rotta di proposito"
git push -u origin test/rompi-build
gh pr create --fill
```
Nella PR vedrai la ❌ rossa. Clicca **Details** e trova l'errore di compilazione nei log.

Correggi, committa, pusha → la PR diventa ✅ verde.
Poi chiudi la PR senza merge (`gh pr close --delete-branch`).

### 3. Rendi la CI obbligatoria

Ora che i check hanno girato almeno una volta, torna nel ruleset di `main`
(lezione 03, *Require status checks*) e aggiungi **Build .NET** e **Build immagine Docker**.
Da adesso **una PR con la CI rossa non si può unire**.

### 4. Aggiungi il badge al README

In cima al `README.md`:
```markdown
![CI](https://github.com/<tuo-utente>/PlayGround/actions/workflows/ci.yml/badge.svg)
```
(ovviamente via branch + PR 😉)

## 🏋️ Esercizio

Aggiungi un progetto di test e fai girare i test in CI:
```bash
git switch -c feat/test-progetto
dotnet new xunit -o PlayGround.Tests
dotnet sln add PlayGround.Tests/PlayGround.Tests.csproj
dotnet test
```
Committa, apri la PR e verifica che nello step **Test** della CI compaiano i test eseguiti.
